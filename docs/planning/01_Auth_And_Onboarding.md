## Overview

Authentication uses Firebase Auth with email/password. The onboarding flow is minimal: sign up, name your gallery, intake your first work. A gallery document is auto-created at signup, linked directly to the user via `ownerId`. There are no roles, no invitations, no multi-user support at MVP.

The "first value" moment is adding their first work with photos within 2 minutes of signing up.

## Auth Method

**Email/password via Firebase Auth.** No social login, no magic links, no SSO at MVP.

Why email/password:

- Simplest Firebase Auth setup
- No third-party OAuth configuration
- Works for users who prefer not to use Google accounts
- Password reset handled entirely by Firebase (built-in email flow)

## Auth Flows

### Sign Up

1. User enters: email, password, confirm password
2. Firebase Auth creates the account
3. App creates the gallery document in Firestore (see below)
4. User lands on the onboarding screen (gallery naming)

**Password requirements**: Firebase defaults (minimum 6 characters). Do not add custom password rules at MVP.

**Email verification**: Deferred to post-MVP. Account is fully usable immediately after signup. Verification adds friction to the first-value moment without meaningful security benefit for a single-user app.

### Sign In

1. User enters: email, password
2. Firebase Auth validates
3. App reads the gallery document using `auth.uid` to find the gallery where `ownerId == auth.uid`
4. User lands on the work list dashboard

### Password Reset

Standard Firebase Auth password reset flow. One screen with an email input, triggers `sendPasswordResetEmail()`. Show confirmation message. No custom email templates at MVP.

### Sign Out

Accessible from a settings or profile area. Calls `signOut()`. Redirects to sign-in screen. Firestore offline cache persists (this is fine -- security rules prevent access without valid auth).

## Gallery Auto-Creation

When a new user signs up, the app immediately creates their gallery document. This happens client-side, not via a Cloud Function.

**Timing**: Gallery creation fires after `createUserWithEmailAndPassword()` resolves successfully, before navigating away from the signup screen.

**Gallery document structure** (see `02_Database_Schema.md` for full schema):

| Field       | Value                                     |
| ----------- | ----------------------------------------- |
| `ownerId`   | `auth.uid` from the newly created account |
| `name`      | Empty string (set during onboarding step) |
| `createdAt` | Server timestamp                          |

**Document ID**: Auto-generated by Firestore. The gallery ID is stored or queried as needed -- the user document does not exist separately. The `ownerId` field on the gallery document is the link.

**Finding the user's gallery**: Query `galleries` collection where `ownerId == auth.uid`, limit 1. This query runs on every app load after auth state confirms a signed-in user. Cache the result in app state for the session.

### Error Handling

If gallery creation fails after auth account creation:

- Retry the Firestore write once
- If still failing (likely offline), Firestore's offline persistence will queue the write and sync when connectivity returns
- The onboarding flow should still proceed since the data will eventually sync

## Onboarding Flow

Onboarding is 2 screens, then the user is in the app. Total target time: under 60 seconds before they can start their first work intake.

### Screen 1: Name Your Gallery

- Single text input: "Gallery name"
- This updates the `name` field on the gallery document
- "Continue" button, disabled until input is non-empty
- No other fields (location, phone, website are all deferred)

### Screen 2: First Work Prompt

- Brief message: "Add your first work to see GalleryLedger in action"
- Two options:
  - **"Add a work now"** -- navigates to the full work intake flow (see `06_Work_Intake.md`)
  - **"Skip for now"** -- navigates to the empty work list dashboard (see `11_Work_List_Dashboard.md`)
- The "Add a work now" path is visually emphasized (primary button) to encourage immediate first-value experience

### Onboarding Completion

- No explicit onboarding flag is stored. The app does not track whether onboarding was completed.
- If the gallery `name` is empty, the app can show the naming screen again on next login. This is the only implicit onboarding state check needed.
- There is no onboarding tour, tooltip walkthrough, or feature introduction. The app should be self-evident.

## Session Management

Firebase Auth handles session persistence automatically.

- **Persistence mode**: `browserLocalPersistence` (default for web). User stays signed in across browser sessions and app restarts.
- **Auth state listener**: Use `onAuthStateChanged()` as the single source of truth for auth state. All routing and data access gates on this listener.
- **Loading state**: Show a loading indicator while auth state is resolving on app startup. Do not flash the sign-in screen before auth state is confirmed.

### Auth State Routing

| Auth State | Gallery Exists | Gallery Name Set | Route To                                |
| ---------- | -------------- | ---------------- | --------------------------------------- |
| Signed out | --             | --               | Sign-in screen                          |
| Signed in  | No             | --               | Gallery creation (error state -- retry) |
| Signed in  | Yes            | No (empty)       | Onboarding Screen 1                     |
| Signed in  | Yes            | Yes              | Work list dashboard                     |

## Device Loss / Switch

All data lives in Firebase (Firestore + Storage). Logging in on a new device restores everything automatically. No local-only data exists except the Firestore offline cache, which rebuilds on first sync.

This is a natural consequence of the architecture but should be stated in any user-facing help or FAQ content: "Your data is backed up to the cloud. Sign in on any device to access your gallery."

## Protected Routes

Every route except sign-in and sign-up requires authentication. Implementation pattern:

- Auth guard wrapper component that checks `onAuthStateChanged` state
- Unauthenticated users redirect to sign-in
- Authenticated users on sign-in/sign-up pages redirect to the dashboard (or onboarding if gallery name is empty)

No role-based route protection at MVP. Every authenticated user has full access to their own gallery. Access to other galleries is prevented by security rules (see `03_Security_Rules.md`), not client-side routing.

- Password input

All screens follow the design system in `04_UI_Design_System.md`. Mobile-first, single-column layout, centered content.
